### LEAD 1: SSRF via `audio_url`/`video_url`/`callback_url` Server-Side Fetch

**Asset:** `api.gladia.io` — `POST /v2/pre-recorded`, `/v2/upload`, `/v2/transcription`, legacy `/audio/text/audio-transcription`, `/video/text/video-transcription`

| Gate | Answer |
|------|--------|
| **Q1 Scope?** | ✅ YES — `api.gladia.io` is HIGHEST |
| **Q2 Reachable?** | ⚠️ KEY-GATED — endpoints return 401 without `x-gladia-key`; BUT CORS `*` + `Access-Control-Allow-Headers: x-gladia-key` (no credentials) means any origin can present an authorized key cross-origin |
| **Q3 Impact?** | ✅ YES — cloud metadata (169.254.169.254) read, internal-network SSRF/timing oracle, callback POST to arbitrary URL (blind SSRF + credential exfil from API origin) |
| **Q4 Read-only proof?** | ❌ NO — requires `POST` with a valid `x-gladia-key` to test; invasive. Passive probes confirm the *surface* (spec says `format:uri` with no scheme allowlist; SDK forwards `audio_url` verbatim) but not the *exploitation* |
| **Q5 Novel?** | ✅ YES — no prior report found in the hunt data |
| **Q6 Not rejected?** | ✅ YES — SSRF is a legitimate vulnerability class, not on the always-rejected list |
| **Q7 Triager accept?** | ⚠️ CONDITIONAL — a triager would accept this *only* with a key-gated POC. Without a valid key, it remains a strong hypothesis |

**Verdict: HOLD**

**Reason:** Strongest lead in the batch (confidence 80 in latest laguna run), but requires a valid `x-gladia-key` for any proof. The *surface* is confirmed by passive means (public OpenAPI spec + SDK source RAG shows zero client-side SSRF guard), but the *exploitation* step is AUTH_HELPED/ invasive. Cannot prove reachability with GET/HEAD alone. Recommend requesting a program-provided trial key before further action.

**Minimal proof steps (if key obtained):**
1. `POST /v2/pre-recorded` with `{"audio_url":"http://<attacker-canary>"}` → observe job baseline
2. Same with `{"audio_url":"http://169.254.169.254/latest/meta-data/"}` → compare `error_code`/`status`/`duration`
3. Same with `{"callback_config":{"url":"http://<attacker-listener>"}}` → confirm server-initiated outbound POST

**CVSS 3.1 (if confirmed):** `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:N/A:N` → **High (8.1)** — Network, Low privilege (key), Changed scope (server-side fetch reads internal assets)

### LEAD 3: Post-OAuth Open Redirect via `redirect_to` Parameter

**Asset:** `app.gladia.io` — `/signin?redirect_to=`

| Gate | Answer |
|------|--------|
| **Q1 Scope?** | ✅ YES — `app.gladia.io` is HIGH |
| **Q2 Reachable?** | ✅ YES — unauthenticated GET reflects `redirect_to` into form action |
| **Q3 Impact?** | ⚠️ MEDIUM — post-auth phishing redirect to attacker-controlled host; OAuth code/state theft if `redirect_uri` injectable |
| **Q4 Read-only proof?** | ⚠️ PARTIAL — passive probe confirms *reflection* (form action contains attacker URL), but *post-auth honoring* requires completing Google OAuth (AUTH_HELPED/HUMAN_ONLY) |
| **Q5 Novel?** | ✅ YES — no prior report |
| **Q6 Not rejected?** | ✅ YES — open redirect is a legitimate finding |
| **Q7 Triager accept?** | ⚠️ CONDITIONAL — reflection alone is not a vulnerability; need proof that the server *honors* the redirect post-authentication |

**Verdict: HOLD**

**Reason:** The reflection surface is confirmed (form action reflects `redirect_to` URL-encoded for `https://evil`, `//evil`, bare-host, `app.gladia.io.evil`, path-only — no host allowlist at the unauthenticated layer). However, `POST /signin` → 302 to `accounts.google.com` with a **hardcoded** `redirect_uri`; OAuth state is an opaque 32-byte random token (not base64url JSON); `redirect_to` is NOT visible in the state cookie or callback URL. Post-auth honoring of `redirect_to` cannot be determined passively. Without a live OAuth completion, this is **reflection without confirmed impact**.

**Minimal proof steps (if authorized session obtained):**
1. `GET /signin?redirect_to=https://evil.example.com` → confirm form action reflects
2. Complete Google OAuth flow with `redirect_to` set
3. Capture final post-auth 302 Location → if it resolves to `evil.example.com`, confirmed

**CVSS 3.1 (if confirmed):** `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N` — **Medium (4.3)** — post-auth phishing redirect

**Reporting channel:** Gladia security channel.

### LEAD 4: WebSocket Auth Token in URL Query Parameter

**Asset:** `api.gladia.io` — `wss://api.gladia.io/v2/live?token=<uuid>`

| Gate | Answer |
|------|--------|
| **Q1 Scope?** | ✅ YES — `api.gladia.io` is HIGHEST |
| **Q2 Reachable?** | ✅ YES — token is bearer-equivalent for live session; leaks via browser history, Referer headers, server/proxy logs |
| **Q3 Impact?** | ✅ YES — token theft enables unauthorized live transcription sessions, access to real-time audio stream |
| **Q4 Read-only proof?** | ⚠️ PARTIAL — OpenAPI spec at `/openapi.json` documents `InitStreamingResponse.url = "wss://api.gladia.io/v2/live?token=<uuid>"`; token format is visible in spec without needing auth |
| **Q5 Novel?** | ⚠️ BORDERLINE — token-in-URL is a well-known anti-pattern; may be considered "best practice" disclosure |
| **Q6 Not rejected?** | ⚠️ BORDERLINE — could fall under "best practice" depending on program appetite |
| **Q7 Triager accept?** | ⚠️ CONDITIONAL — many programs accept token-in-URL as Medium; others reject as design choice |

**Verdict: HOLD**

**Reason:** The OpenAPI spec *publicly documents* that WebSocket auth uses a token in the URL query parameter. This is confirmed by passive reads of `/openapi.json` (no auth required). However:
- Token theft impact depends on token lifetime/rotation (untested, requires AUTH_HELPED)
- Token-in-URL is a widely-known anti-pattern; many programs classify this as Low or best-practice rather than a vulnerability
- No evidence that the token is long-lived or that a stolen token grants access beyond the session

**CVSS 3.1 (if accepted):** `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N` — **High (7.5)** — if token is long-lived and grants full session access

**Reporting channel:** Gladia security channel. Worth including as a LOW/MEDIUM finding if Lead 1 or Lead 2 is accepted in the same report.

### LEAD 5: CORS Wildcard + `x-gladia-key` Header Permitted Cross-Origin

**Asset:** `api.gladia.io`

| Gate | Answer |
|------|--------|
| **Q1 Scope?** | ✅ YES — `api.gladia.io` is HIGHEST |
| **Q2 Reachable?** | ✅ YES — `Access-Control-Allow-Origin: *` with `Access-Control-Allow-Headers: x-gladia-key` |
| **Q3 Impact?** | ❌ LOW — wildcard without `Access-Control-Allow-Credentials` means no credentialed cross-origin reads; only public endpoints (`/v1/models`, `/openapi.json`, `/health`) are readable cross-origin, and they're already public |
| **Q4 Read-only proof?** | ✅ YES — confirmed via passive OPTIONS probe |
| **Q5 Novel?** | ✅ YES |
| **Q6 Not rejected?** | ❌ **REJECTED** — CORS wildcard without credentials is a common misconfiguration with minimal security impact when no sensitive data is exposed cross-origin; this is a "best practice" finding |
| **Q7 Triager accept?** | ❌ NO — a reasonable triager would reject this as Low/info-only |

**Verdict: INVALID**

**Reason:** CORS `Access-Control-Allow-Origin: *` without `Access-Control-Allow-Credentials` is not exploitable for cross-origin reads of authenticated data. The only cross-origin-readable content is already public (`/v1/models`, `/openapi.json`, `/health`). This is a best-practice observation, not a vulnerability.
